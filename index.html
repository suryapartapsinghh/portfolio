    Reporting latency for finance and leadership

    Financial reporting pipeline

    The problem. The nightly batch finished around 2 am. By the time finance opened their dashboards the data was six to eight hours old, and any correction waited a full day to appear. Decisions were being made on yesterday’s numbers.

    What I did. Replaced full-refresh logic with Delta Change Data Feed and Spark Structured Streaming so only changed records flow on each run. Ran the new pipeline alongside the old one through a validation period, then retired the old job.

    Before24 h
    After15 min
    • No more full-table scans; each run touches only what changed.
    • Monitoring, retries and alerting built in, so it’s easier to operate than what it replaced.
    • Platform-wide Spark tuning of partitioning, shuffle, join strategy and cluster config lifted end-to-end throughput by 30%.
    50%

    Faster time to insight for analytics and reporting teams

    Medallion lakehouse platform

    The problem. Several teams each maintained their own copy of the same source data with slightly different logic. Reports disagreed and nobody could say which number was right.

    What I did. Led the design of a single Bronze/Silver/Gold lakehouse for clinical, pharmacy and financial data, where every transformation rule lives once and every consumer reads the same Gold tables. Five to ten terabytes a day from more than ten upstream systems.

    # Read only what changed since the last run, then merge into Silver
changes = (spark.read.format("delta")
    .option("readChangeFeed", "true")
    .option("startingVersion", last_processed_version)
    .table("bronze.claims")
    .filter("_change_type in ('insert', 'update_postimage')"))

(DeltaTable.forName(spark, "silver.claims").alias("t")
    .merge(conform(changes).alias("s"), "t.claim_id = s.claim_id")
    .whenMatchedUpdateAll()
    .whenNotMatchedInsertAll()
    .execute())
    • Wrote the layer contracts: raw append-only ingestion, conformed schemas, business-ready Gold, so every team knew what to expect at each stage.
    • Standardized ingestion into a documented template; onboarding a new source takes 40% less time.
    • OCR-driven ingestion for unstructured patient documents, feeding clinical analytics and ML.

    Fewer data incidents reaching downstream teams

    Data quality and observability

    The problem. Schema drift, late-arriving data and sudden volume drops were all being discovered in dashboards, hours after the fact, by the people least able to fix them.

    What I did. Built checks at every medallion layer and wired them into CI/CD so bad data can’t be deployed. Freshness and volume monitors alert before a consumer notices anything.

    Schema driftColumn contracts checked at deploy; the build fails before the pipeline does
    Bad valuesGreat Expectations suites per layer; rows quarantined with a reason, not dropped
    Late dataFreshness SLAs per table, alerting when a source goes quiet
    Volume dropsAnomaly detection on row counts against a rolling baseline
    • Deployment time down 25% from the same CI/CD work across GitHub Actions, Azure DevOps and ARM Templates.
    • The bigger change was cultural: teams stopped double-checking shared datasets and started building on them.
